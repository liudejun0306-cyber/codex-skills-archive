# 技能维护

仅在用户明确要求修改、清理、重构、安装或打包技能时读取；正常办案不得读取。

## 修改原则

修改前先判断问题属于：触发边界、路由冲突、重复规则、输出质量、工具/格式、知识沉淀或打包归档。优先删除重复、冲突和过度具体的规则，再判断是否确需增加内容。

主 `SKILL.md` 只保留定位、基础规则、路由和停止条件；专项内容放在对应 workflow、capability 或独立技能。不要把用户的一次性案件事实、法律观点、裁判规则、版本日志、聊天背景或长篇方法论原样堆入技能。

## 冲突控制

1. 一个任务只使用一个主技能或一个主要 workflow；专项技能只在边界清楚时触发。
2. `legal-practice` 负责具体案件、请求权或抗辩、证据分析、法律文书和证据成果；`china-contract-practice` 负责合同起草与修改；`obsidian-legal-kb-sync` 负责知识沉淀、专题摘录和索引。
3. 相同通用规则只保留一处。其他文件只写“适用主规则”或通过路由引用，不重复展开。
4. 修改任何技能时，应考虑是否会增加不必要 token；能拆到 references 并按需读取的，不放在主 `SKILL.md`。

## 打包和归档

1. 用户要求“打包技能”时，压缩包默认放桌面，不放入 `/Users/liudejun/Desktop/材料/04codex/技能`。
2. `/Users/liudejun/Desktop/材料/04codex/技能` 只保留可阅读的技能文件夹，不放 `.zip`、旧归档、临时包或 `.DS_Store`。
3. 打包前先同步安装目录和桌面技能副本；打包后校验 zip 完整性。
4. 清理重复包时，优先保留技能文件夹和已安装版本，删除同名 zip、旧总归档和无对应技能的孤立压缩包。

## 校验

每次修改后检查：

1. 技能是否通过 `quick_validate.py`；
2. 一个任务是否只加载一个主要 workflow；
3. capability 或 reference 是否最少必要；
4. 同一规则是否重复；
5. 链接和引用是否有效；
6. 金额计算、Word 输出、原文摘录、知识同步等高频能力是否仍可独立调用。

验证完成后再交付。不得把版本日志写入技能正文。
